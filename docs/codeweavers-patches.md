## What matters for Cross

### Required for D3DMetal (keep, and match the D3DMetal version)

- **22435** `dlls/ntdll/ntdll.spec:1767`, `dlls/ntdll/loader.c:3919`: ntdll exports
  `__wine_unix_call` (as `__wine_unix_call_exported`). The D3DMetal PE DLLs (`d3d11.dll`,
  `d3d12.dll`, `dxgi.dll`, `atidxx64.dll`) import it to reach their unix half.
- **22434** `dlls/ntdll/loader.c:2287` + `dlls/ntdll/unix/loader.c:1180-1240`: on the first
  *native* PE module load ntdll calls `unix_pe_module_loaded`, which (once, only on macOS 14+)
  `dlopen`s `$CX_APPLEGPTK_LIBD3DSHARED_PATH` and calls its `register_non_native_code_region`
  for every native PE image. `scripts/winecx-env.sh` sets the variable.
- **23015** `dlls/ntdll/unix/unix_private.h:584`, `server.c:1941`, `sync.c`, `thread.c`:
  `GPT_ABI_WRAPPER` turns `NtClose`, `NtCreateSemaphore`, `NtReleaseSemaphore`,
  `NtCreateEvent`, `NtSetEvent`, `NtResetEvent`, `NtClearEvent`, `NtPulseEvent` and
  `NtCreateThreadEx` in ntdll.so into trampolines: if the caller's return address lies inside
  `libd3dshared.dylib` the ms_abi variant runs, otherwise the normal sysv one. D3DMetal calls
  these unix-side functions directly.
- **`dlls/winemac.drv/d3dmetal.c`** (no marker): the exported `macdrv_functions` table
  (24 pointers, `C_ASSERT(sizeof == 192)`). D3DMetal 3.0 expects a different table (it also
  resolves `wine_get_dos_file_name` / `wine_get_unix_file_name`), which is why our build only
  works with D3DMetal 2.1 (see NOTES.md). This file and its `Makefile.in` line are what has to
  change to support 3.0/4.0.
- **24067** `dlls/ntdll/unix/loader.c:148,377`, `loadorder.c:253`: ntdll.so exports
  `prepend_dll_path()`, `add_load_order_override()`, `KeServiceDescriptorTable` and
  `simulate_writecopy` with default visibility. Nothing in the Wine tree calls them; CrossOver's
  closed `lib/wine/x86_64-unix/cxcompatdb.so` does (`strings` on
  `downloads/crossover/CrossOver.app/Contents/SharedSupport/CrossOver/lib/wine/x86_64-unix/cxcompatdb.so`
  shows both names). **This is how CrossOver puts D3DMetal ahead of Wine's own d3d11/d3d12/dxgi**
  (`prepend_dll_path` inserts a directory before `dll_dir`), which explains the NOTES finding
  that WINEDLLPATH alone cannot do it. We currently move Wine's DLLs aside instead; a tiny
  unix-side helper of our own calling `prepend_dll_path` would be the cleaner equivalent.
- **23560** `dlls/setupapi/devinst.c:4499`: the GPU LUID reported by setupapi is taken from
  D3DMetal's dxgi so both agree (Diablo IV, generally useful).
- **23042** `dlls/wined3d/adapter_gl.c:3795`: AMD-style D3D9 driver version because D3DMetal
  reports an AMD GPU ("AMD Compatibility Mode").

### macOS loader and process plumbing (keep; some need our attention)

- **22144** `dlls/ntdll/unix/loader.c:497,570,703` + `configure.ac` "Crossover hacks": ntdll
  builds the loader path as `<bindir>/wineloader` and exec's a descriptively named link to the
  preloader so the Dock shows the game's name. CodeWeavers' `make install-image` rule renames
  `bin/wine` to `bin/wineloader`; plain `make install` (which we use) does not, hence the
  `bin/wineloader -> wine` link in `scripts/build-winecx.sh`.
- **13438** `loader/main.c:38,268`, `dlls/ntdll/unix/loader.c:573`: process / app-menu name
  taken from the .exe name.
- **10913** `loader/wine_info.plist.in`: the loader's embedded Info.plist says
  `com.codeweavers.CrossOver.wineloader` and "CrossOver-Hosted Application". `strings
  runtimes/winecx/bin/wine` shows these strings in our current build. **Must be changed
  before we ship** (CodeWeavers' bundle id and trademark; see docs/LICENSING.md).
- **12735** `dlls/advapi32/advapi.c:51`, `dlls/shell32/shellpath.c:2621`: Windows user name
  is always `crossover` unless `CX_REPORT_REAL_USERNAME` is set. Decide whether Cross keeps a
  fixed name (portable prefixes) under a name of our own; the string `crossover` is hardcoded.
- **10523 / 23741** `dlls/ntdll/unix/process.c:91,225,944`: the "alternative loader" hands
  process creation to the CrossOver app over the socket in `CX_ALT_LOADER_SOCKET`. Inactive
  when the variable is unset (our case). A future Cross.app could use the same hook.
- **24717** `dlls/ntdll/unix/process.c:888`: a PE-side environment variable named
  `__CX_UNIX_FOO=bar` becomes `FOO=bar` in the Unix environment of the new process. Useful to
  pass DYLD/MTL/D3DM settings from Windows-side launchers.
- **CX_WINDOWS_VERSION** (`dlls/ntdll/version.c:505`, unnumbered): environment override of
  the reported Windows version.
- **24711** `dlls/ntdll/unix/system.c:1221,1290,1420`: `WINENCPU` limits the reported CPU
  count (this Mac reports `hw.ncpu` = 16).
- **22996** `WINE_SIMULATE_WRITECOPY`; **17634** `WINE_LARGE_ADDRESS_AWARE`.
- **20810** `WINEWOW6432BPREFIXMODE` "32-bit bottle" mode: not needed (we create 64-bit
  prefixes with new WoW64).
- **3853** `WINE_WAIT_CHILD_PIPE`: CrossOver launcher plumbing, unused by us.
- **10151** `dlls/bcrypt/gnutls.c:386`, `crypt32/unixlib.c`, `secur32/schannel_gnutls.c`:
  libgnutls is `dlopen`ed by a list of sonames; on macOS that means a leaf name
  (`libgnutls.30.dylib`), which is why `DYLD_FALLBACK_LIBRARY_PATH` must include
  `runtimes/winecx/lib`.

### Synchronization: msync is in our build

`dlls/ntdll/unix/msync.c` / `server/msync.c` are compiled on `__APPLE__` and enabled with
`WINEMSYNC=1`. `strings runtimes/winecx/bin/wineserver` contains `WINEMSYNC` and the msync
messages, so **our winecx wineserver supports msync**, unlike the GPTK 3.0 build that NOTES.md
describes as esync-only. The `cross` CLI and `winecx-env.sh` only set `WINEESYNC=1`; msync is
untested on winecx. Caveat: the wineserver shipped in the CrossOver 25.1.0 trial
(`downloads/crossover/CrossOver.app/Contents/SharedSupport/CrossOver/CrossOver-Hosted Application/wineserver`)
contains no esync/msync strings at all, so CodeWeavers' own macOS build does not appear to use
either; treat msync as experimental.

### Rosetta 2 workarounds (keep all; we run x86_64 under Rosetta)

**18947** cross-process code writes re-translated; **20760** wow64cpu `lretq` thunks;
**22131** / **21217** fake debug registers (ntdll and wineserver `mach.c`); **24256** /
**24265** correct MXCSR in signal handlers (M3 and later); **20186** CET instructions as NOP;
**24945** write fault on W|X pages; **20218** longer service start timeout;
**18576** display modes on Apple Silicon; **16371** low-memory release for OpenGL;

### Rebasing onto newer Wine

Most CORE hacks are small and local (ntdll, winemac.drv, wow64cpu, server/mach.c). The large
pieces are esync/msync and `d3dmetal.c`. For D3DMetal 3.0/4.0 the reference would be newer
CrossOver sources (26.x) at `https://media.codeweavers.com/pub/crossover/source/`, diffed the
same way.
